# ADR-0008: Division Engineer Upload — Postgres Binary Alignment

## Status
**Implemented — 2026-04-04**

## Context

The Division Engineer document upload panel (POW, DUPA, CONTRACT in `DetailedProjInfo.jsx`) was broken in three independent ways despite the backend binary storage pipeline being functional:

### Problem 1: PostgreSQL Type Inference Failure (`42P18`)
`jsonb_build_object` accepts variadic `"any"` arguments. When a `$N` placeholder is passed as the *key* argument (e.g., `jsonb_build_object($8, $9::jsonb)`), PostgreSQL cannot determine the type at parse time and throws:
```
error: could not determine data type of parameter $8
code: 42P18
```
This affected 5 call sites across the engineer document UPSERT queries.

### Problem 2: Frontend Ignored API Response
`handleAtomicUpload` in `DetailedProjInfo.jsx` set the project's PDF path to a hardcoded legacy disk path after every upload:
```js
const expectedPath = `/uploads/project_docs/${project.ipc}_${key}.pdf`;
```
The API returns the actual Postgres binary path (`/api/asset/{binary_id}`) in `resData.filePath`, but this was never read. As a result, the Download button immediately pointed to a nonexistent file.

### Problem 3: PyMuPDF Owner-Password Lock
PDFs with owner-password flags (even those requiring no user password to open) cause `fitz.open()` to return a locked document object. All page operations on a locked document throw `"document closed or encrypted"`. The retry branch re-opened the file but also never authenticated, hitting the same error.

### Problem 4: Python Executor Chain Masked Real Errors
The executor chain (`python` → `py`) meant any real Python error immediately triggered a `py` fallback that always failed with "not recognized" on this VM — masking the actual root cause in the logs.

## Decision

### Fix 1: Explicit `::text` Cast on `jsonb_build_object` Keys
All 5 call sites updated: `jsonb_build_object($N::text, $M::jsonb)`

### Fix 2: Response-Driven Path Update
`handleAtomicUpload` now reads the response body and uses the server-returned `filePath`:
```js
const resData = JSON.parse(await res.text());
const actualPath = resData.filePath || resData.data?.filePath || legacyFallback;
```
This mirrors the pattern already established in `DocumentUpload.jsx` (School Head Unit 1).

### Fix 3: Authenticate After Open
`doc.authenticate("")` called immediately after every `fitz.open()` in `compress_pdf.py`. This unlocks owner-password-protected PDFs without requiring the actual password, which is the correct approach for PDFs that are "open" but flagged.

### Fix 4: Smart Executor Loop
Replaced the nested try/catch chain with a loop over `['python', 'python3', 'py']`:
- Silently skips absent executors (detected via OS "not recognized" error messages)
- Breaks immediately on real Python errors — avoids pointless retries
- Applied to both Hydra and compression paths

## The Reference Pattern
The working baseline for all document uploads in this system is the **School Head Unit 1 Ownership Document** (`DocumentUpload.jsx` → `POST /api/schools/:iern/ownership-docs`):
- Uses `memoryUpload.single('file')` — file stays in memory as a Buffer
- Passes through `compressBufferTo96Dpi()` and `upsertBinary()`
- Returns `{ data: { filePath, id, fileName, file_size } }`
- Frontend reads `result.data.filePath` and stores it in state

The Division Engineer upload now follows this same contract end-to-end.

## Consequences

- **Positive**: POW, DUPA, and CONTRACT uploads now store correctly in Postgres and the frontend immediately reflects the correct `/api/asset/:id` path.
- **Positive**: Hydra sharding resumes for PDFs > 1.5MB with owner-password flags (the most common case in Philippine government documents).
- **Positive**: Compression failures are now diagnosable — real Python errors are logged at their actual source instead of being masked by a failing `py` fallback.
- **Rule**: All future document upload endpoints in this system must return `filePath` at the top level of the response JSON (or at `data.filePath`), and all frontend upload handlers must read from the response rather than constructing paths client-side.
